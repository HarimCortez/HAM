# ham-test-engineer — conventions and gotchas (step 1: skeleton/roles/authz/audit/outbox/auth)

## Independent oracle pattern (foundation.md §9.1)
- `tests/authz/expected_matrix.csv` is generated by `tests/authz/generate_expected_matrix.py`
  (run it and commit the CSV after a **deliberate, reviewed** change — never to "make a test
  pass"). The generator hand-types role name **strings** (not imported from `ham.authz.roles`)
  and a from-scratch `ORACLE` dict re-derived from PRD §67/§4.11/§68 + the decided
  `docs/prd-open-questions.md` rows (Q-041, Q-045, Q-054, Q-055, Q-021, Q-080, Q-081) — it
  must never import `ham.authz.matrix.MATRIX` itself, or it stops being independent.
  `tests/authz/test_expected_matrix.py` replays every row through `ham.authz.matrix.authorize`
  and also asserts the oracle's action set == `MATRIX`'s (so a new action can't silently ship
  uncovered). All ~500 generated rows passed cleanly against the real matrix on first
  write-up — no bugs found there as of this slice.
- Cases encoded per action: baseline (per role), zero_role, unauthenticated, disabled_user,
  scope_out_of_bounds (SELF-scope "someone else's record"), mfa_role_unverified_alone/
  _union_with_volunteer (Q-045), role_union (Volunteer+Administrator). `impersonation.stop`
  is special-cased (scope = "currently impersonating", not a normal allowed-roles set).
- Route-coverage (`tests/authz/test_route_coverage.py`) walks the **real** URLconf via
  `django.urls.get_resolver()`, not a hand-maintained list — catches a new view shipping
  without `@requires_action(...)` or a `PUBLIC_ROUTES` entry. Also checks every declared
  action exists in `MATRIX`, and every `PUBLIC_ROUTES` name resolves to a real URL (catches a
  stale entry after a rename).
- `nav_for` per-persona (`tests/authz/test_nav_personas.py`) iterates
  `ham.identity.management.commands.seed_dev.PERSONAS` directly (not a hand-picked subset) so
  a new/changed seed persona is checked automatically. Expected nav keys per role are a
  hand-typed dict cross-referencing `ham/authz/matrix.py`'s per-action allowed-roles with
  which nav items are `built=True` this slice — update `_EXPECTED_BY_ROLE` when a new nav
  item's `built` flag flips.

## Audit-coverage without a live DB call per command (foundation.md §9.2)
- `tests/audit/test_command_registry.py` finds every real `@command("x")` site by **regexing
  source with `^@command\(` (MULTILINE, anchored at column 0)** — anchoring matters: a
  docstring *example* of the decorator pattern (e.g. `ham/outbox/services.py`'s module
  docstring, which shows callers how to wrap `retry_delivery`) is indented and would
  false-positive as a real usage without the anchor. Excludes `ham/authz/commands.py` itself
  (its own docstring/type hints use the literal placeholder `"action.code"`).
- Not every mutating `MATRIX` action is wired via `@command`: `audit.export`
  (`ham/authz/audit_access.py::export_csv`) re-implements authorize→step-up→atomic→record by
  hand because it needs to return raw CSV bytes and lives one layer above where `@command` is
  defined — tracked as `MANUALLY_WIRED_ACTIONS` in the registry test, not a gap.
  `me.sign_in_email.change` (Q-083) and `requester_pii.reveal` (Q-081) are genuine
  not-yet-built placeholders (`PLACEHOLDER_ACTIONS`). Read-only actions (`.view`/`.list`/
  `rules.view`/etc.) never get a `@command` at all (`READ_ONLY_ACTIONS`).
- The pre-existing `tests/authz/test_commands.py` (generic pipeline mechanics: rollback
  atomicity, denial audit, impersonation-blocked audit, step-up-without-recording) and
  `tests/identity/test_impersonation.py` (both-identities-on-one-event) already covered the
  *behavioral* half of §9.2 well before this pass — don't duplicate them; the registry test
  above only adds the "is every action actually wired, exactly once" static check.

## A real bug found by building the Playwright smoke suite
- `ham/web/views_audit.py::audit_export`'s `StepUpRequired` handler passes `request.path`
  (`/audit/export`, POST-only) as the step-up `next=`. `ham/web/auth_views.py::step_up`'s
  success handler always does a **GET** redirect to `next`. So a real browser's very next
  request after entering the TOTP code is `GET /audit/export` → Django's
  `require_http_methods(["POST"])` refuses it with 405 — the export never completes on the
  first attempt. `tests/web/test_admin_screens.py::test_audit_export_requires_step_up`
  (pre-existing) never caught this because it manually re-POSTs a third time instead of
  following the redirect chain like a browser would. Contrast with
  `admin_impersonate`/`admin_mfa_reset`, whose `next` is a GET+POST confirm *page* (works
  fine with a GET). Filed as `tests/web/test_audit_export_stepup_redirect_bug.py`
  (`xfail(strict=True)`); suggested fix in that file's docstring is to redirect to
  `reverse("web:audit_log")` instead of `request.path`. **Route around this in any new
  Playwright test that exercises audit export**: click "Export" a second time after the
  step-up form submits (step-up is fresh for the rest of that session) rather than expecting
  the immediate post-step-up navigation to succeed.

## Playwright (`tests/e2e/test_smoke.py`) gotchas
- **`DJANGO_ALLOW_ASYNC_UNSAFE=1` is required** whenever a test calls Django ORM code (e.g.
  `ham.jobs.run_due_jobs_now()`, or fixture setup) from inside a `sync_playwright()` block —
  Playwright's "sync" API actually runs the test body inside a greenlet on a thread driving an
  internal asyncio loop, and Django's ORM refuses DB access if it detects a running loop in
  the current thread. Set `os.environ.setdefault("DJANGO_ALLOW_ASYNC_UNSAFE", "1")` at module
  scope (this is a documented Playwright/Django interaction, not a HAM-specific workaround).
- **Don't call `page.wait_for_url(...)` right after a `page.click(...)` that causes
  navigation** — Playwright's `click()` already waits for the resulting navigation to finish,
  so a subsequent `wait_for_url` call starts listening *after* the navigation event already
  fired and times out waiting for one that will never come again. Just assert on `page.url`
  directly after the click.
- **`send_transactional_email` (sign-in codes) is deferred, not synchronous** — it inserts a
  Procrastinate job row; nothing lands in `django.core.mail.outbox` until
  `ham.jobs.run_due_jobs_now()` runs in the test process. `live_server` runs the app in a
  background thread of the *same process* against the *same real Postgres DB*
  (`@pytest.mark.django_db(transaction=True)` is required for `live_server` — committed rows
  are visible cross-thread), so this works, but you must call `run_due_jobs_now()` yourself
  after the browser triggers the send.
- **Two blocked-while-impersonating actions this slice's UI can demonstrate for a plain
  Volunteer persona**: almost none render a clickable affordance for a Volunteer (they gate
  the MFA-recovery-codes/trusted-devices buttons behind `mfa_required`/`is_enrolled`, which a
  Volunteer never has) — but the **route guard itself** (`ham/authz/guard.py`) refuses *any*
  `blocked_while_impersonating` action outright before the view runs, so simply `page.goto`-ing
  a GET screen for such an action (e.g. `/me/security`, action `me.security.manage`) while
  impersonating already lands on the neutral "isn't available" page — no button-hunting or
  hand-built JS `<form>` submission needed.
- One flaky-looking but harmless artifact: a `PytestWarning: Error when trying to teardown
  test databases: ... "test_ham_tests" is being accessed by other users` after a
  `live_server`/`transaction=True` test — a `live_server` worker thread keeps a pooled
  connection open past test teardown. It's a warning, not a failure, and doesn't affect
  subsequent runs in the same `pytest` invocation; if a *separate* invocation fails to create
  the test DB afterward, `dropdb test_ham_tests` (or `test_<your DATABASE_URL db name>`)
  clears it.
- Full run cost as of this slice: 2 smoke scenarios (390px + 1280px) add ~15s to a suite that
  otherwise runs in ~5s (790 passed total in ~20s) — comfortably inside the "under ~60s, keep
  it in the normal `pytest` run" budget from foundation.md §9.7. If it ever gets slower/flakier,
  gate it behind a marker like `tests/e2e/test_shell_screenshots.py`'s `HAM_SCREENSHOTS=1`
  pattern and document the opt-in command in the module docstring.
- Frontend must be built once (`cd frontend && npm ci && npm run build`) before any Playwright
  test that loads a real page, or `{% static %}`-served assets referenced by `web/base.html`
  (icons.svg sprite, fonts.css) 404 silently in a way that doesn't fail the test but would
  break real visual QA.

## General repo/test-run gotchas (still true as of this slice)
- Own Postgres DB: `DATABASE_URL=postgres://postgres@localhost:5432/ham_tests` (trust auth,
  already running). `PYTHONPATH=.` from the worktree root. Full command used throughout this
  slice:
  `DATABASE_URL=postgres://postgres@localhost:5432/ham_tests PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers PYTHONPATH=. /home/user/HAM/.venv/bin/python -m pytest -q`
- `/home/user/HAM/.venv/bin/` has the working `mypy`/`django-stubs`/`ruff` toolchain (prefer it
  over any bare `mypy`/`ruff` on PATH). `mypy` only checks the **bodies** of functions that
  themselves have a type annotation (return type or params) — an untyped helper (no `->`
  annotation) silently skips body checking, which is why some pre-existing test helpers using
  a bare string for a UUID field never tripped mypy; a newly-annotated helper doing the same
  thing will.
- Playwright's Chromium is preinstalled at `/opt/pw-browsers` in this sandbox — never run
  `playwright install` here. In CI (fresh runner), the workflow now runs
  `playwright install --with-deps chromium` before the test step (`.github/workflows/ci.yml`).
- `tests/web/test_no_hardcoded_church_or_colors.py` now also scans **Python** source (not just
  templates) under `ham/` and `config/` for the literal forbidden church-name strings
  (`test_no_literal_church_name_in_python_source`), per foundation.md §9.6's fuller wording
  ("templates/Python outside design-system/").

## Step 2 (Intake) gap-filling pass (2026-09-28)

### `ham.requester_portal.services` lookup-globals test isolation
- `services.register_request_facts_lookup`/`register_request_contact_lookup`/
  `register_email_to_request_ids_lookup` are process-global mutable state, set once for real
  at `RequesterPortalConfig.ready()`. Several test files' `autouse` fixtures register either
  the *real* callables or *fakes* for the duration of their own tests, then used to reset the
  globals to `None` on teardown -- fine only if that file happened to be the *last* one in
  the session to touch them; any later test/file that assumed `ready()`'s registration was
  still intact would then get a spurious `RuntimeError`.
- Fixed by adding one shared fixture, `real_portal_lookups`, to top-level `tests/conftest.py`.
  It re-registers the exact real callables (duplicated from `RequesterPortalConfig.ready()`,
  not by calling `ready()` again, which would also re-register the periodic purge jobs) both
  on setup **and** on teardown.
  - Files that want the *real* lookups for their own tests (`tests/requester_portal/
    test_submission_flow.py`, `test_notifications.py`, `tests/web/
    test_requester_portal_screens.py`): their own `autouse` fixture just takes
    `real_portal_lookups` as a parameter and does nothing else in its body.
  - Files that want *fakes* for their own tests but must not corrupt global state for
    whoever runs next (`tests/requester_portal/test_links.py`, `test_regenerate_and_find.py`):
    their own `autouse` fixture takes `real_portal_lookups` as a parameter too, purely for
    **fixture teardown ordering** (pytest tears down in reverse setup order, so
    `real_portal_lookups`'s teardown — re-register real — runs *after* the local fixture's
    own `services._request_facts_lookup = None` reset, so the real ones win either way,
    regardless of file/test order). The local fixture's body still registers its own fakes
    exactly as before; only the dependency was added.
- Lesson for next time: don't trust "this fixture resets to `None`, so it must be safe" —
  check whether `None` really is a safe idle state, or whether it's standing in for "whatever
  `ready()` set up", which is not the same thing once *this* isn't the first/only test file
  that touches that global in the session.

### Runtime-registry-based tests for "was this decorator's side effect triggered" are
inherently order-dependent within one pytest session — use a static source check instead
- `ham.jobs.periodic_job` (like any decorator) only runs when the module defining it is
  *imported*. A test that inspects `ham.jobs.app.periodic_registry.periodic_tasks` at runtime
  to check "did job X get registered" is checking a **process-wide, one-time** side effect:
  once *any* test anywhere in the session imports that module (directly or transitively — a
  lazy function-body import inside a service function counts too, the moment that function is
  first called), the registration sticks for every test that runs afterward in the same
  process, silently changing the answer depending on file/test order.
- Concretely: an early draft of `tests/jobs/test_periodic_registry.py` used
  `app.periodic_registry.periodic_tasks` directly. It correctly caught the
  `RequestsConfig.ready()` bug (below) when `tests/jobs/` happened to run early
  (alphabetically first), but two of its assertions **spuriously passed** when the suite ran
  in reverse file order, because `tests/web/*` (which calls `submit_request` a lot) had
  already run first and incidentally imported the buggy module. Caught by this task's
  "run the suite twice, forward and reverse" step — always do this after adding any test that
  inspects shared/global registration state.
- Fixed by rewriting the check to be **static**: regex-scan each app's `apps.py::ready()`
  source (`_ready_imports_submodule` in `tests/jobs/test_periodic_registry.py`) for whether it
  imports the module that defines the periodic job, rather than asking Procrastinate's live
  registry whether it happened to get imported by *something* by the time this test runs. A
  static check reads the same source text no matter what ran before it. Two regex passes are
  needed (not one collapsed-whitespace regex): one for parenthesized multi-line
  `from . import (\n a,\n b,\n)` (a DOTALL search naturally bounded by the closing `)`), one
  per-line for non-parenthesized single-line imports (which have no reliable terminator other
  than the newline itself once there's more than one `from ... import` statement in the same
  method body).
- Real bug found this way (High severity, reported in the hand-back): `ham/requests/
  apps.py::RequestsConfig.ready()` never imports `ham.requests.jobs`, so
  `requests.retention_sweep` (Q-127: 7-year requester-PII erase after close, 90-day spam
  purge) never registers with Procrastinate's periodic runner in a real
  `manage.py procrastinate worker` process. Pinned as an `xfail(strict=True)` bug file
  (`tests/jobs/test_requests_retention_sweep_not_registered_bug.py`), same pattern as
  `tests/web/test_audit_export_stepup_redirect_bug.py`. A second, same-shape, step-1-scope
  instance also exists (`ham/identity/apps.py::ready()` never imports `.authn`, so
  `identity.purge_sign_in_challenges` never registers either) — not fixed this slice (out of
  step-2 scope) but listed in `KNOWN_NOT_WIRED_DUE_TO_BUG` so the enumeration test doesn't
  silently miss it. `identity.sweep_idle_impersonation_sessions` (also step 1) turned out to
  be a false alarm under the static check: it *is* registered at real startup, but only via an
  indirect chain (`RequestsConfig.ready()` → `.notifications` → `ham.identity.services` →
  `.impersonation`, all module-level imports) that this table's one-job/one-ready-file model
  can't cleanly express — deliberately left out of `EXPECTED_PERIODIC_JOBS` with a comment
  explaining why, rather than forced into a misleading row.

## Step 3 (Approvals) gap-filling pass (2026-09-29)

### The `real_portal_lookups` shared fixture pattern is a real, recurring order-dependence
trap — audit EVERY new file for it, not just the one that seems related
- Step 2's write-up above already names the fix (`tests/conftest.py::real_portal_lookups`) and
  the exact failure mode (a local fixture that resets `services._request_facts_lookup` etc. to
  `None` on teardown instead of restoring the real callables). Step 3 shipped **four more**
  independent copies of the same pre-fix local fixture, never migrated to the shared one:
  `tests/web/test_fix_b_media_gallery.py`, `tests/requester_portal/
  test_fix_a_verification_security.py`, `test_fix_b_email_links.py`, `test_fix_a_intake_
  source.py`. None of these failed on their own, or even in the *forward* file-order full
  suite — only running the whole suite in **reverse file order** (`pytest` has no built-in
  `--reverse`; build the list with `find tests -name 'test_*.py' | sort | tac` and pass it as
  plain, explicit `pytest` arguments — command substitution like `$(...)` and writing a
  wrapper script both got refused by this sandbox's git-safety heuristic as "too complex to
  verify doesn't run git"; a literal, fully-expanded argument list is fine) surfaced it: one of
  these files runs early in reverse order, poisons the module-level globals to `None` on its
  own teardown, and every *later* file that assumed either app-startup registration or an
  earlier restore was still intact then hit `RuntimeError: ham.requester_portal.services used
  before ham.requests registered its request-facts lookup` — including two `tests/e2e/`
  Playwright files (`test_step3_requester_screens.py`, `test_fix_f1_upload.py`) nowhere near
  the actual bug. **Fix pattern**: change the local fixture's signature to take
  `real_portal_lookups` as a parameter (even with an empty body, or dropping the body
  entirely if it registered nothing else) so its teardown restores the real callables instead
  of `None` — don't just delete the local fixture, since some files (e.g. `test_links.py`,
  `test_regenerate_and_find.py`) *do* need their own fakes mid-test and correctly already
  depend on `real_portal_lookups` purely for teardown-ordering safety (see step-2 write-up).
  `tests/requester_portal/test_app_ready_registration.py` had a related but distinct problem:
  its own docstring admitted it only works if it runs *first alphabetically* within its
  directory (to observe genuine post-`ready()` state before any sibling's fixture touches the
  globals) — true in forward order, false in reverse order (it sorts near the *end* of its

### Sandbox tool-use note: multi-file `pytest` invocations and the "too complex to verify"
git-safety heuristic
- Any Bash command combining `python -m pytest` with command substitution (`$(...)`), a
  written-then-executed wrapper script, or other non-literal shell constructs gets refused in
  this worktree-isolated sandbox with "cannot be shown not to be git" — even though nothing in
  the command touches git. Work around it by fully expanding the file list into a single,
  literal, flat argument list in the one `Bash` call (e.g. build the reversed file list with a
  separate, simple `find | sort | tac` call first, inspect it, then paste the expanded list as
  plain arguments) rather than trying to feed pytest a computed list at invocation time.
